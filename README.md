# hls-parser

`hls-core`에서 시간 검색과 세그먼트 갱신 비용을 비교합니다. 세그먼트 수, 검색 패턴, 자료구조를 바꿔 각 작업에 걸리는 시간을 확인합니다.

## 시간 검색

`WallClockTimeline`은 한 재생목록의 세그먼트를 실제 날짜와 시각으로 찾는 객체입니다. 이번 실험에서는 `WallClockTimeline::locate`와 `PlaylistTracker::locate`를 비교합니다. 두 함수 모두 원하는 시각에 해당하는 세그먼트를 바이너리 서치로 찾습니다. 여기에 위치를 추정하거나 직전 검색 결과를 활용하는 세 가지 방식을 추가해 비교합니다.

샘플용 재생목록에서는 실제 재생목록처럼 세그먼트의 재생 시간이 조금씩 다르다고 가정합니다. 각 세그먼트의 재생 시간을 2.0~2.4초로 지정합니다. 앞 세그먼트가 끝나는 시각에 다음 세그먼트가 시작하도록 만듭니다.

측정 전에는 검색을 200번 미리 실행합니다. 이 과정을 워밍업이라고 합니다. 검색을 반복하면 사용하는 코드와 데이터가 CPU 캐시라는 빠른 메모리에 올라가면서, 처음 실행할 때와 여러 번 실행한 뒤의 검색 시간이 달라질 수 있습니다.

이번 실험은 검색을 반복하는 상태에서의 평균 시간을 비교하므로, 준비용 검색 200번은 측정에서 제외합니다. 워밍업을 마친 뒤 타이머를 시작하고, 세그먼트 수와 관계없이 각 방식으로 검색을 2,000번씩 반복합니다. 표의 값은 워밍업 이후의 검색 시간이며, 프로그램을 처음 실행해서 첫 검색을 하는 데 걸리는 시간은 보여주지 않습니다. 검색용 목록과 `bucket`의 표를 만드는 시간도 제외합니다.

<details>
<summary>비교한 검색 방식과 예시</summary>

- `interpolation`: 찾는 시각이 전체 시간 범위에서 차지하는 비율로 세그먼트 위치를 추정합니다. 총 100초인 영상에서 80초를 찾는다면 전체 세그먼트의 80% 지점 근처부터 확인합니다. 세그먼트 길이가 비슷하면 추정이 잘 맞을 수 있습니다.
- `hinted`: 직전에 찾은 세그먼트를 먼저 확인합니다. 찾는 시각이 그 안에 없으면 앞이나 뒤로 탐색 거리를 1칸, 2칸, 4칸씩 늘립니다. 찾을 범위를 잡은 뒤에는 그 범위를 반씩 줄이며 정확한 위치를 찾습니다. 재생바를 조금씩 움직일 때 앞서 찾은 위치를 활용할 수 있습니다.
- `bucket`: 시간을 1초 단위로 나누고, 각 칸에 검색을 시작할 세그먼트 위치를 표로 기록합니다. 80.3초를 찾는다면 80초 칸을 읽고 그 위치부터 확인합니다. 검색 범위를 빠르게 좁힐 수 있지만 표를 만드는 시간과 추가 메모리가 필요합니다.

</details>

### 검색 패턴별 결과

세그먼트 수를 450개, 1,800개, 9,000개, 100,000개로 바꿔 가며 세 가지 검색 패턴을 비교합니다.

여기서 검색은 원하는 시각에 해당하는 세그먼트를 찾는 작업입니다. 세 가지 패턴은 검색할 시각을 고르는 방법입니다.

1. **무작위 이동**

   매번 전체 재생 구간에서 시각을 무작위로 고릅니다. 예를 들어 5분, 1분, 8분처럼 앞뒤로 크게 건너뛰며 검색합니다.

2. **연속 이동**

   재생 구간의 앞에서 뒤로 일정한 간격을 두고 검색합니다. 재생바를 왼쪽에서 오른쪽으로 쭉 드래그하는 상황입니다. 재생바를 드래그 할 때 움직이는 속도가 달라지는것을 고려하여 각 검색 시각에는 최대 0.08초 정도의 가변값을 추가합니다. 예를 들어 10초를 검색할 경우 9.95초나 10.03초를 검색하도록 설정합니다.

3. **이동 후 미세 조정**

   먼저 시각 하나를 무작위로 고릅니다. 이후에는 직전 검색 시각에서 앞뒤로 최대 0.05초씩 움직이며 24번 더 검색합니다. 재생바에서 원하는 위치를 누른 뒤 조금씩 조정하는 상황입니다.

각 패턴에서 검색은 2,000번 합니다. 멀리 떨어진 시각을 찾을 때와 가까운 시각을 계속 찾을 때, 검색 방식별 성능이 어떻게 달라지는지 비교합니다.

| 검색 방식 | 무작위 이동 | 연속 이동 | 이동 후 미세 조정 |
|:---|---:|---:|---:|
| `WallClockTimeline` | 18 | 16.5 | 16 |
| `PlaylistTracker` | 19 | 17 | 17 |
| `interpolation` | 18 | 12.5 | 10 |
| `hinted` | 45 | 14 | 4 |
| `bucket` | 5 | 3 | 2 |

단위는 검색 한 번당 나노초(ns)입니다. 검색 2,000번에 걸린 총시간을 2,000으로 나누고, 각 검색에 걸리는 시간은 따로 측정하지 않습니다. 표는 10개 프로세스에서 얻은 평균 시간의 중앙값입니다.

- **바이너리 서치 (`WallClockTimeline`, `PlaylistTracker`)**: 세 패턴의 측정값은 각각 16~18ns, 17~19ns입니다. 9,000개 조건에서는 검색 패턴에 따른 두 함수의 시간 차이가 작습니다.
- **`interpolation`**: 위치를 추정하는 방식의 이점은 연속 이동과 미세 조정에서 나타납니다. 각각 12.5ns와 10ns로 기준 함수인 `WallClockTimeline`보다 낮고, 무작위 이동에서는 기준 함수와 같은 18ns입니다.
- **`hinted`**: 가까운 시각을 반복해서 찾는 미세 조정에서는 4ns로 기준 함수의 16ns보다 낮습니다. 시각을 무작위로 고르는 패턴에서는 45ns로 기준 함수의 18ns보다 높습니다. 직전 검색 결과를 활용하는 방식은 검색할 시각이 얼마나 가까운지에 따라 차이가 큽니다.
- **`bucket`**: 세 패턴 모두에서 가장 낮은 값인 5ns, 3ns, 2ns를 보입니다. 이 결과는 검색 시간만 비교한 것이며, 검색 위치를 기록한 표를 만드는 비용과 추가 메모리는 측정하지 않습니다.

대체 구현의 결과는 시간 정보가 연속된 합성 입력에서만 대조합니다. 시간 정보가 비어 있는 구간의 동작은 함께 검증하지 않습니다.

### 세그먼트 수에 따른 결과

세그먼트 수에 따라 `WallClockTimeline::locate`와 `PlaylistTracker::locate`의 검색 시간이 어떻게 달라지는지 비교합니다. 각 조건에서 무작위로 시각을 골라, 그 시각에 해당하는 세그먼트를 2,000번 검색합니다. 검색 횟수는 같고, 검색 대상인 목록의 크기를 바꿉니다.

| 세그먼트 수 | `WallClockTimeline` | `PlaylistTracker` |
|---:|---:|---:|
| 450 | 10 [9–10] | 11 [10–11] |
| 1,800 | 12 [12–14] | 13 [13–15] |
| 9,000 | 18 [17–19] | 19 [18–20] |
| 100,000 | 32 [29–39] | 37.5 [31–151] |

단위는 검색 한 번당 나노초(ns)입니다. 프로그램을 새로 실행할 때마다 검색 2,000번의 총시간을 2,000으로 나눠 평균 시간을 구합니다. 이 과정을 10번 반복합니다. 대괄호 앞의 값은 평균 시간 10개의 중앙값이며, 대괄호 안의 숫자는 실행별 평균 시간의 범위입니다. 각 검색에 걸리는 시간은 따로 측정하지 않습니다.

이번 측정에서 세그먼트 수를 450개에서 100,000개로 약 222배 늘리면, 검색 시간의 중앙값은 `WallClockTimeline`에서 10ns에서 32ns로 약 3.2배, `PlaylistTracker`에서 11ns에서 37.5ns로 약 3.4배 늘어납니다. 목록이 커져도 검색 시간이 항목 수에 비례해 늘지는 않습니다. 다만 100,000개 조건의 `PlaylistTracker`는 실행별 평균 시간이 31~151ns로 실행에 따라 차이가 납니다.

## 자료구조

실시간 재생목록 갱신은 새 세그먼트를 기존 목록의 뒤에 추가합니다. 기존 목록 앞에 더 과거 시점의 세그먼트를 추가하며, 아래 표는 자료구조별로 추가 작업에 걸린 시간을 비교하여 정리합니다.

세그먼트 하나를 나타내는 기록에는 번호와 시작 시각, 끝 시각만 넣습니다. 각각 8바이트이므로 기록 하나는 24바이트입니다. 이 기록을 다음 네 자료구조에 저장합니다.

| 표기 | 저장 방법 |
|:---|:---|
| `sorted-vec` | `Vec`에 번호순으로 저장합니다. 앞에 항목을 넣으면 기존 항목을 뒤로 옮깁니다. |
| `offset-vec` | `Vec`에서 목록이 시작되는 위치를 따로 기억합니다. 앞쪽 항목을 제외할 때 시작 위치를 옮기고, 남은 빈 공간은 과거 항목을 추가할 때 재사용합니다. 공간이 부족하면 기존 항목을 옮깁니다. |
| `ring-deque` | `VecDeque`로 목록의 앞뒤에 항목을 추가하거나 제거합니다. |
| `btree` | 시작 시각으로 항목을 찾는 맵과 세그먼트 번호로 시작 시각을 찾는 맵을 따로 둡니다. 둘 다 `BTreeMap`을 사용합니다. |

실험은 가장 최근 1,800개 항목이 담긴 목록에서 시작합니다. 이후 더 오래된 항목이 포함된 1,800개짜리 묶음을 차례로 넣습니다. 각 묶음에는 이미 보관한 항목도 일부 포함하며, 중복 항목은 다시 넣지 않고 새 항목만 기존 목록 앞에 추가합니다.

숫자를 줄여 10개짜리 묶음을 넣는 예시로 보면 다음과 같습니다. 이 예시에서는 번호가 작을수록 더 오래된 세그먼트입니다.

1. 기존 목록에는 **10번~19번** 세그먼트가 있습니다.
2. 여기에 더 오래된 **1번~10번** 묶음을 넣습니다.
3. **10번은 이미 있으므로** 중복해서 넣지 않습니다.
4. 새로운 **1번~9번만** 목록 앞에 추가합니다. 추가 후 목록에는 **1번~19번**이 있습니다.

실제 실험에서는 묶음끼리 보통 10%가 겹치도록 정합니다. 따라서 1,800개짜리 묶음 하나에는 다음 항목이 포함됩니다.

- 새로 추가할 과거 항목 **1,620개**
- 이미 보관한 중복 항목 **180개**

마지막 묶음은 전체 구간의 첫 항목부터 1,800개로 구성합니다. 새로 추가할 과거 항목이 1,620개보다 적게 남으면, 이미 보관한 항목과 겹치는 부분이 더 커집니다. 예를 들어 9,000개 조건의 마지막 묶음에는 새 항목 720개와 중복 항목 1,080개가 포함됩니다.

아래 표는 묶음 하나를 기존 목록에 합치는 데 걸리는 시간을 비교합니다. 입력은 1,800개이지만 실제로 새로 저장하는 항목 수는 중복을 제외한 수입니다.

| 세그먼트 수 | `sorted-vec` | `offset-vec` | `ring-deque` | `btree` |
|---:|---:|---:|---:|---:|
| 9,000 | 3.88 | 3.96 | 2.19 | 142.6 |
| 100,000 | 27.75 | 27.37 | 1.71 | 150.9 |
| 1,000,000 | 253.4 | 256.5 | 3.98 | 156.0 |

단위는 1,800개 항목의 묶음 하나당 마이크로초(µs)입니다. 묶음별 비용의 프로세스 중앙값을 구한 뒤, 30개 프로세스의 중앙값을 집계합니다. 과거 구간을 모두 추가하는 데 걸린 총시간은 아닙니다. 1,000,000개는 현재 기본 보관 상한인 100,000개를 넘는 규모를 시험하는 조건입니다.

- **`sorted-vec`**: 9,000개 조건의 3.88µs에서 1,000,000개 조건의 253.4µs로 추가 시간이 크게 늘어납니다. 앞에 항목을 넣을 때 기존 항목을 뒤로 옮기는 방식이므로, 목록이 커질수록 옮겨야 할 항목도 많아집니다.
- **`offset-vec`**: 3.96µs에서 256.5µs로 늘어 `sorted-vec`와 비슷한 값을 보입니다. 이번 실험에서는 앞쪽에 재사용할 빈 공간이 없어, 시작 위치를 따로 두어도 기존 항목을 옮기는 작업을 피하지 못합니다.
- **`ring-deque`**: 세 규모 모두에서 추가 시간이 가장 낮으며, 중앙값은 1.71~3.98µs입니다. 앞에 항목을 추가하는 작업에서 목록 크기에 따른 측정값의 차이는 두 배열보다 작습니다.
- **`btree`**: 142.6µs에서 156.0µs로 목록 크기에 따른 증가 폭은 작습니다. 9,000개와 100,000개 조건에서는 다른 세 자료구조보다 시간이 길지만, 1,000,000개 조건에서는 두 배열보다 짧습니다.
